### 1-4. 표기 규칙
- **공사** — 한국관광공사
- **공사 OpenAPI** — 한국관광공사 국문 관광정보 서비스(`KorService2`) 및 관련 오퍼레이션
- **판정 필드** — 검수 판정에 실제로 사용하는 공사 응답 필드
- **검수 지문** — 판정 필드로 생성한 SHA-256 해시값
- **finding** — 규칙 1건이 산출한 문제 1건
- **AC** — 인수조건(Acceptance Criteria). 해당 요구사항의 완료 판정 기준
- 요구사항 문장은 "…해야 한다" 형태로 통일한다.
### 1-5. 설계 제약 (전 요구사항 공통 전제)
<callout icon="🔒" color="red_bg">
	아래 5개 제약은 **모든 기능 요구사항에 우선한다.** 요구사항과 충돌하면 제약이 이긴다.
</callout>
1. **표시하는 것은 항상 실시간, 저장하는 것은 판정 근거뿐** — 화면에 보이는 관광지·행사 정보는 그 순간 공사 OpenAPI를 호출한 결과여야 한다. 관광지 원문(개요·이미지·주소·설명)은 저장하지 않는다.
2. **AI는 정규화하고, 규칙엔진이 판정한다** — 등급·점수·충돌 여부의 판정은 결정론적 규칙엔진이 내린다. 동일 입력에는 반드시 동일 결과가 나와야 한다.
3. **모르는 것은 모른다고 말한다** — 데이터가 없거나 해석에 실패하면 "확인 불가"로 명시하고, 정상 판정을 내리지 않는다.
4. **예측하지 않고 관측한다** — 판매량·시장 반응을 예측한다고 표현하지 않는다. 공사 데이터에서 관측 가능한 사실만 제시한다.
5. **비표출 콘텐츠는 노출하지 않는다** — `showflag`가 0으로 전환된 콘텐츠의 정보는 화면·리포트에 표시하지 않는다. (공사 승인 회신의 의무 조항)

## 2. 기능 구조 개요
### 2-1. 4단계 기능 흐름
```plain text
① 입력            ② 검수                  ③ 수정                  ④ 감시
F01 상품 등록   →  F03 운영정보 해석    →  F08 패치 제안       →  F12 변경 감지
F02 관광지 확정    F04 검수 엔진 실행 ⭐    F09 확정·자동 재검수    F13 영향 상품 탐색
                   F05 등급·출시 준비도    F10 수정 전후 비교      F14 수요 신호
                   F06 검수 결과 조회      F11 검수 리포트
                   F07 확인 필요 목록
                                   ⑤ 운영 : F15 호출 예산 관리 · F16 설정
```
②까지가 "린터", ③이 "자동 수정", ④가 타 서비스에 없는 영역이다.

### 8-1. F12 · 데이터 변경 감지 ⭐
<callout icon="🧬" color="blue_bg">
	**원문을 저장하지 않고 어떻게 "바뀌었다"를 아는가**
