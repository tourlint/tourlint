## 1-2. 제품 정의
> 개발자가 코드를 배포하기 전에 린터로 오류를 잡듯이, 관광상품도 판매하기 전에 휴무일·행사기간·이동시간·일정충돌·수요 적합성을 자동으로 검사한다.<br>그리고 배포된 코드의 의존성이 바뀌면 알려주듯이, 출시된 상품의 관광 데이터가 바뀌면 알려준다.
린터 은유가 정확한 이유가 하나 더 있습니다. 린터는 **소스코드를 복제해 보관하지 않습니다.** 검사 시점에 읽고, 결과와 규칙 버전만 남깁니다. TourLint의 데이터 아키텍처도 동일한 성질을 갖습니다 (6장).

## 2-4. 출시 이후의 공백
검수는 **한 번 하고 끝나지 않습니다.** 상품을 출시한 뒤에도 관광지는 임시휴관하고, 운영시간은 바뀌고, 축제는 일정이 변경되거나 취소됩니다.
<callout icon="💡" color="yellow_bg">
	한국관광공사는 연간 수천에서 수만 건의 관광 데이터를 현행화합니다.
	그 변경이 이미 판매 중인 상품에 반영되지 않으면, 고객은 문 닫은 곳 앞에 서게 되고 **책임은 상품을 판 쪽에 있습니다.**
	그럼에도 상품 출시 이후의 데이터 변경을 추적해주는 도구는 조사한 범위에서 발견되지 않았습니다.
</callout>
TourLint가 단순 일정 검사기와 갈라지는 지점이 여기입니다.
<callout icon="🔎" color="orange_bg">
	**문제 규모의 정량 근거 확보 계획 (W1\~W2)**
	위 서술의 타당성을 확보하기 위해 **공사 데이터로 직접 측정되는 수치와 공개된 도구의 기능 조사** 두 가지로 근거를 확보합니다.
	**① 변경 빈도 정량화 — ✅ 30일간 측정 완료 (2026.08.05)**
	관광 콘텐츠는 **평일 하루 평균 98건, 최대 177건**이 수정됩니다. 주말에는 갱신되지 않습니다.
	더 중요한 것은 **표출/비표출 전환**입니다. 평상시에는 하루 한 자릿수이지만, **2026-07-28 하루에 3,206건이 한꺼번에 조회 불가 상태로 전환**되었습니다. 관광지가 삭제되는 것이 아니라 그냠 안 나오게 되는 것이므로, 수정일자만 보고 있으면 놓칩니다.
	이는 공사 OpenAPI만으로 산출된 검증 가능한 수치이며, **이미 판매 중인 상품이 하루아침에 대량으로 깨질 수 있다**는 것을 보여줍니다
	**② 대체재 조사 (W2)** — 기존 여행 업무 도구·관광 플랫폼의 변경 추적 기능 유무를 조사합니다
	②의 결과가 예상과 다를 경우 서술 수위를 낮추고 **①의 정량 근거만으로** 문제를 제시합니다.
</callout>
## 2-5. TourLint의 해결 흐름
```plain text
상품 등록
   ↓
공사 OpenAPI 실시간 조회로 관광지·행사 연결
   ↓
운영 오류 + 수요 적합성 자동 검수 → 등급 판정 + 출시 준비도 산출
   ↓
수정 패치 제안 → 적용 → 자동 재검수
   ↓
검수 지문 기록 (원문은 저장하지 않음)
   ↓
[출시 후] 재조회 → 지문 비교 → 변경 감지 + 수요 신호 탐지
   ↓
영향받는 상품 탐색 → 담당자 알림 → 패치
```

# 3. 목표와 사용자
## 3-1. 서비스 목표
1. 분산된 관광정보와 검수 작업을 **하나의 플랫폼으로 통합**한다
2. 상품 검수와 수정에 필요한 **시간을 단축**한다
3. 관광정보·행사·수요에 변화가 생기면 **영향받는 상품을 빠르게 찾아낸다**
4. 기존 상품을 처음부터 다시 만들지 않고 **수정 가능한 부분만 패치**한다
5. 수정된 상품이 실제로 운영 가능한지 **자동으로 재검증**한다
6. 상품 출시 이후에도 정보 변경을 감지해 **최신 상태를 유지**한다
1\~2번은 지정과제의 *프로세스 파편화*에, 3\~6번은 *공급 지연과 트렌드·수요 적기 대응 실패*에 각각 대응합니다.
## 3-2. 핵심 타깃
**1차 타깃** — 데이터 분석 전담 인력 없이 관광상품을 빠르게 기획하고 출시해야 하는 실무자
- 중소 여행사 상품기획자
- 지자체 관광과 담당자
- 지역관광재단 실무자
- 지역관광추진조직 (DMO)
- 관광상품 운영 대행사
- 로컬 투어 기획자
공통점은 **검수에 쓸 시간과 인력이 없다는 것**입니다. 대기업 여행사처럼 전담 검수 인력을 두지 못하는 조직일수록 효용이 큽니다.
## 3-3. 사용자 페르소나
<callout icon="👩" color="gray_bg">
	**지역 여행사 상품기획자 김지현**
	김지현 씨는 다음 달 강릉 1박 2일 상품을 출시해야 합니다. 상품 초안은 하루 만에 썼습니다.
	문제는 그다음입니다. 관광지 기본정보, 휴무일과 운영시간, 축제 개최기간, 장소 간 이동시간, 비 올 때 대체 일정, 요즘 뜨는 콘텐츠, 일정표 작성, 팀 내 수정 의견 취합 — 이 여덟 가지를 각각 다른 창구에서 처리해야 합니다.
	그리고 상품을 출시한 뒤에도 마음이 놓이지 않습니다. 출발 전에 관광지 운영시간이 바뀌지 않았는지 확인할 방법이 없기 때문입니다.
	**TourLint를 쓰면** 일정표를 올린 뒤 운영 오류와 수요 적합성을 한 번에 확인하고, 문제가 있는 일정에 수정안을 적용하고, 출시 이후의 데이터 변경은 알림으로 받습니다.
</callout>

# 5. 설계 원칙
모든 기술 결정은 아래 네 가지에서 파생됩니다.
## 원칙 1. 표시하는 것은 항상 실시간, 저장하는 것은 판정 근거뿐
<callout icon="1️⃣" color="blue_bg">
	사용자 화면에 보이는 모든 관광지·행사 정보는 **그 순간 한국관광공사 OpenAPI를 호출한 결과**입니다.
	데이터베이스에는 관광지 원문(개요, 이미지, 주소, 설명)을 **한 글자도 저장하지 않습니다.**
	저장하는 것은 "언제 어떤 콘텐츠를 조회해서 어떤 판정을 내렸는가"라는 **검수 이력**뿐입니다.
	다만 공사 데이터 자체의 갱신 주기에서 오는 시차는 존재합니다. 그 범위와 한계는 6-6-b에 명시하고 화면에도 함께 표기합니다.
</callout>
## 원칙 2. AI는 정규화하고, 규칙엔진이 판정하고, 원문은 항상 병기한다
<callout icon="2️⃣" color="blue_bg">
	공사 API의 운영정보는 자유 텍스트입니다. AI는 이를 구조화된 형태로 **정규화**만 합니다.
	오류 여부의 **판정은 결정론적 규칙엔진**이 내립니다. 같은 입력이면 언제나 같은 결과가 나옵니다.
	그리고 판정 화면에는 **공사 원문을 그대로 함께 표시**합니다. 사용자는 언제나 근거를 직접 검증할 수 있습니다.
</callout>
## 원칙 3. 모르는 것은 모른다고 말한다
<callout icon="3️⃣" color="blue_bg">
	운영정보가 없거나 해석에 실패하면 **"확인 불가"로 명시**하고 정상 판정을 내리지 않습니다.
	확인 불가 항목은 리포트에 **별도 섹션으로 모아** "출시 전 운영기관 직접 확인 필요 목록"으로 제공합니다.
	데이터 공백을 숨기지 않는 것이 실무자에게 가장 실질적인 가치입니다.
</callout>
## 원칙 4. 예측하지 않고 관측한다
<callout icon="4️⃣" color="blue_bg">
	TourLint는 상품 판매량이나 시장 반응을 **예측한다고 주장하지 않습니다.**
	제공하는 것은 **공사 데이터에서 관측 가능한 사실**뿐입니다. 이 지역에 신규 콘텐츠가 몇 건 늘었는가, 여행기간 중 행사가 몇 건 열리는가, 상품 타깃이 기대하는 콘텐츠 유형이 일정에 포함되어 있는가.
	해석과 판단은 기획자의 몫으로 남깁니다.
</callout>

# 6. 데이터 아키텍처 — 검수 지문
## 6-1. 해결해야 할 요구사항
두 가지 요구가 동시에 걸립니다.
<table fit-page-width="true" header-row="true">
<tr>
<td>요구</td>
<td>내용</td>
</tr>
<tr>
<td>실시간성</td>
<td>화면에 표시하는 관광정보는 항상 최신이어야 한다. 관광 데이터를 로컬에 복제해 보관하면 동기화가 어긋날 때 잘못된 정보가 서비스되고 책임은 개발사에 있다</td>
</tr>
<tr>
<td>변경 감지</td>
<td>"관광지 정보가 바뀌었다"를 감지하려면 논리적으로 **이전 상태**를 알아야 한다</td>
</tr>
</table>
원문을 저장하지 않으면서 이전 상태를 아는 구조가 필요합니다.
## 6-2. 저장 대상이 두 가지로 갈립니다
공사 API는 휴무일 정보를 이런 **문장**으로 줍니다.
```plain text
restdate = "매주 월요일 휴관 (공휴일인 경우 익일 휴관)"
```
TourLint는 이 문장을 두 단계로 다룹니다.
<table fit-page-width="true" header-row="true">
<tr>
<td>구분</td>
<td>정체</td>
<td>저장 여부</td>
</tr>
<tr>
<td>**원문**<br>`"매주 월요일 휴관..."`</td>
<td>공사가 만들고 공사가 관리하는 데이터</td>
<td>❌ **저장하지 않음**</td>
</tr>
<tr color="green_bg">
<td>**정규화 결과**<br>`weeklyClosed = MON`</td>
<td>**TourLint가 그 문장을 읽어 만든 판독 결과**</td>
<td>✅ **저장함**</td>
</tr>
</table>
둘째 줄이 핵심입니다. 이것은 공사 데이터의 **복사본이 아니라 자체 산출물**이므로 보관에 제약이 없습니다. 변경 감지에서 "이전 값"으로 쓰는 것도 원문이 아니라 이 판독 결과입니다.
<callout icon="🩺" color="green_bg">
	**건강검진 기록과 같은 구조입니다**
	병원은 작년에 뽑은 **혈액을 냉동보관하지 않습니다.** 대신 "2025년 혈압 120/80"이라는 **판독 결과**만 남겨둡니다.
	올해 다시 가면 새로 재고, 작년 기록과 비교해 "혈압이 올랐습니다"라고 말해줍니다. 샘플 자체를 쌓아둘 필요가 없습니다.
	TourLint도 관광지 데이터 원본을 보관하지 않고, 검수할 때마다 새로 조회해 판독한 뒤 **그 판독 결과만 남깁니다.**
</callout>

## 6-4. 변경 감지 동작
```plain text
1) 재검수 시각에 공사 OpenAPI를 다시 호출한다
2) 응답에서 modifiedtime과 판정 필드를 추출한다
3) 판정 필드로 지문(SHA-256)을 새로 만든다
4) 직전 검수 지문과 비교한다
   - 동일  → 변경 없음. 판정 재사용 가능
   - 상이  → 변경 감지. 재판정 후 담당자 알림
```
## 6-5. 변경 이력을 보여주는 방법
판독 결과가 남아 있으므로 **무엇이 어떻게 바뀌었는지**까지 표시됩니다.
```plain text
[9월 15일 검수]   지문 a3f91c  →  판독 { 휴무: [월],     운영: 09:00-18:00 }
[9월 20일 재검수] 지문 7b2e04  →  판독 { 휴무: [월, 화], 운영: 09:00-17:00 }

화면 표시 :
  휴무일    월 → 월·화         (화요일 휴무가 새로 추가됨)
  운영시간  18시까지 → 17시까지  (1시간 단축)
  영향      '강릉 1박 2일' 2일차 14시 일정이 화요일에 해당 → 차단으로 승격

현재값 옆에는 재조회한 공사 원문을 그대로 병기한다
```
<table fit-page-width="true" header-row="true">
<tr>
<td>보여줄 수 있는 것</td>
<td>보여줄 수 없는 것</td>
</tr>
<tr>
<td>휴무일·운영시간·행사기간 등 **판정 필드의 판독값 이력**</td>
<td>공사 원문 텍스트 자체의 diff (예: overview 문장이 어떻게 다듬어졌는지)</td>
</tr>
<tr>
<td>변경 시점과 공사 수정일자(modifiedtime)</td>
<td>판정에 사용하지 않는 필드의 변화</td>
</tr>
<tr>
<td>변경이 판정에 미친 영향 (정상 → 차단 승격 등)</td>
<td>검수한 적 없는 기간의 변화 (검수 시점 사이의 공백)</td>
</tr>
<tr>
<td>영향받는 상품과 구체적 일정 구간</td>
<td>공사 이미지의 변경 전 모습</td>
</tr>
</table>
<callout icon="⚖️" color="blue_bg">
	**검수 도구에 필요한 것은 원문의 diff가 아니라 판정에 영향을 주는 값의 변화입니다.**
	실무자가 알아야 하는 것은 "개요 문장이 어떻게 다듬어졌는가"가 아니라 **"화요일 휴무가 생겨서 내 상품이 깨졌는가"** 입니다.
	판정에 쓰는 필드는 전부 판독 결과로 남기고 있으므로 실무상 필요한 이력은 모두 커버됩니다.
</callout>
## 6-6. 낡은 정보가 노출될 수 없는 구조
저장된 판독 결과는 **화면에 "현재 정보"로 표시되지 않습니다.**
<table fit-page-width="true" header-row="true">
<tr>
<td>화면 영역</td>
<td>표시되는 값</td>
</tr>
<tr>
<td>관광지 정보 · 검수 판정 근거</td>
<td>항상 **그 순간 호출한 실시간 값**</td>
</tr>
<tr>
<td>변경 이력 칸</td>
<td>"9월 15일에 이렇게 판단했다"는 **과거 판독 기록**</td>
</tr>
</table>
## 6-6-b. 실시간 호출의 범위와 한계
"실시간"이 의미하는 것은 **호출 시점 기준으로 공사가 제공하는 최신 상태**입니다. 공사 OpenAPI는 콘텐츠 수정일 기준으로 매일 정해진 시각에 동기화되며, 당일 수정분은 익일부터 조회됩니다. 따라서 원천 데이터에는 최대 1일의 반영 지연이 존재합니다.
<table fit-page-width="true" header-row="true">
<tr>
<td>구분</td>
<td>TourLint가 보장하는 것</td>
<td>보장하지 않는 것</td>
</tr>
<tr>
<td>데이터 신선도</td>
<td>호출 시점에 공사가 제공하는 최신 값</td>
<td>공사에 아직 반영되지 않은 당일 변경</td>
</tr>
<tr>
<td>저장값 노출</td>
<td>저장된 판독 결과를 현재 정보로 표시하지 않음</td>
<td>—</td>
</tr>
<tr>
<td>감지 범위</td>
<td>공사 데이터에 반영된 모든 변경</td>
<td>공사 데이터에 없는 현장 상황 (당일 임시휴관 등)</td>
</tr>
</table>
<callout icon="🕐" color="gray_bg">
	**이 한계는 숨기지 않습니다.** 검수 근거 영역에 함께 표기하며, 출발 임박 상품에 대해서는 확인 필요 목록에 "출발 전 운영기관 최종 확인" 항목을 자동 생성합니다.

## 7-2. 출시 준비도
```plain text
출시 준비도 = 100
             - (차단     건수 × 25)
             - (오류     건수 × 10)
             - (주의     건수 ×  4)
             - (확인불가 건수 ×  3)
             하한 0점

차단이 1건이라도 있으면 점수와 무관하게
화면에 "출시 불가" 배지를 표시하고 출시 승인을 막는다
```
단순하고 설명 가능한 산식을 의도적으로 선택했습니다. 실무자가 점수 변화를 직접 예측할 수 있어야 신뢰를 얻습니다. 가중치는 설정 화면에서 조정 가능합니다.
<callout icon="🧮" color="green_bg">
	**본 문서의 모든 준비도 점수는 위 산식에서 도출된 값이며 검산 가능합니다.**
	수정 전 — 차단2·오류1·주의2·확인불가1 → 감점 50+10+8+3 = 71 → **29점**
	수정 후 — 차단0·오류0·주의1·확인불가1 → 감점 0+0+4+3 = 7 → **93점**
	화면에는 **점수와 확인 필요 건수를 분리 표기**합니다 — `출시 준비도 93점 · 확인 필요 3건`. 확인 불가를 감점 대상으로 두되, 그 사유가 공사 데이터 결측임을 드러내기 위해서입니다.
	다만 **6-6-b의 D+1 구조적 시차로 생성되는 "출발 전 확인" 항목은 감점 대상이 아닙니다.** 데이터 결측과 구조적 시차를 구분합니다.
	사용자가 무시(dismiss)한 항목은 점수에서 제외하되 리포트에 건수를 명시합니다. **차단 등급은 무시할 수 없습니다.**
</callout>

## 7-4. 공사 OpenAPI 단독 판정 규칙
### R01. 휴무일 · 운영시간 충돌 — 차단
```plain text
일정      : 10월 13일(월) 10:00 A미술관 방문
공사 원문 : restdate = "매주 월요일"
정규화    : 주간휴무 = MON / 신뢰도 = 확정
판정      : 차단 — 휴무일에 방문 일정이 등록되어 있습니다
```
수정안 — 방문 날짜 변경 / 일정 순서 교체 / 반경 20km 내 동일 유형 관광지로 대체
### R02. 행사기간 불일치 — 차단
```plain text
상품 출발일 : 10월 15일
공사 원문   : eventStartDate=20261001, eventEndDate=20261012
판정        : 차단 — 해당 행사는 여행일 이전에 종료됩니다
```
수정안 — 여행일과 겹치는 동일 지역 행사로 교체 / 해당 일정 제거
### R03. 일정 시간 중복 — 오류
```plain text
14:00~15:30 박물관 (소요시간 90분 — 종료시간 미입력 시 기본 체류시간 테이블 보완, FR-IN-011)
15:00~16:00 카페
판정 : 오류 — 두 일정이 30분 중복됩니다
```
### R04. 콘텐츠 편중 — 주의
`contentTypeId`와 신분류체계 기준으로 동일 유형 반복을 감지합니다.
```plain text
1일차 : 카페 3곳 + 해변 2곳
판정  : 주의 — 동일 유형 관광 콘텐츠가 과도하게 반복됩니다
```
단, 상품 콘셉트에 "카페투어" 등 반복이 의도된 키워드가 있으면 판정에서 제외합니다.
### R05. 데이터 검증 불가 — 확인 불가
```plain text
공사 응답 : restdate 결측 / usetime = "홈페이지 참조"
판정      : 확인 불가 — 운영시간을 데이터에서 확인할 수 없습니다
            출시 전 운영기관에 직접 확인을 권장합니다
```
<callout icon="🚫" color="red_bg">
	**정보가 없다는 이유로 임의로 정상 판정을 내리지 않습니다.** 원칙 3의 구현입니다.
</callout>

```plain text
재판정          : 관람 가능 시간 20분 → 오류로 승격
알림            : 9월 25일 출발 '부산 야경투어'의 A전망대 운영시간이 변경되었습니다
```

	공사는 승인 회신에서 "showflag가 비표출(0)로 변경된 콘텐츠는 서비스에서 노출되지 않도록 처리되어야 한다"고 명시했습니다. 회신 전체에서 **의무형으로 쓰인 유일한 문장**이므로 선택적 기능이 아닙니다.
	관광지가 삭제되는 것이 아니라 표출 상태가 바뀌는 것이며, 이미 판매 중인 상품에 포함된 관광지가 비표출되면 그것도 현장 사고로 이어집니다.
	동기화 목록 조회가 `showflag` 파라미터와 응답 필드를 모두 제공하므로, **배치에서 ****`showflag=0`****으로 별도 조회해 감지**합니다.
</callout>
### R06-b. 콘텐츠 비표출 전환 — 차단
상품 일정에 포함된 콘텐츠의 `showflag`가 0으로 전환되면 해당 일정을 **차단(Blocker)** 으로 판정하고, 그 관광지 정보를 화면에서 내립니다.
<callout icon="🚫" color="red_bg">
	**사유를 알 수 없다는 사실 자체가 차단 근거입니다.**
	공사가 표출을 중단한 이유는 API 응답으로 알 수 없습니다. 운영 중단일 수도, 콘텐츠 통합이나 일시적 비표출일 수도 있습니다.
	확인되지 않은 상태의 관광지를 판매 중인 상품에 남겨두는 것은 원칙 3에 어긋나며, 공사가 노출 중단을 요구한 이상 그 관광지를 근거로 한 판정도 유지할 수 없습니다.
</callout>

<td>명칭·주소를 재출력하지 않고 contentid와 전환 감지 시각만 기재</td>
</tr>
</table>
비표출 콘텐츠의 저장된 판독 결과는 **과거 판정 이력으로만** 남기며, 현재 정보로 화면에 표시하지 않습니다.
일정 항목 자체는 **자동으로 삭제하지 않습니다.** 담당자가 변경 사실을 인지하고 대체안을 선택하는 것이 원칙이며, 시스템은 판정하고 제안할 뿐입니다. 자동 삭제하면 담당자가 무엇이 왜 사라졌는지 알 수 없게 됩니다.
### R10. 상품 타깃-콘텐츠 적합성 — 주의
주관적 판단을 배제하기 위해 **기대 콘텐츠 프로파일 테이블**을 사전에 정의하고, 실제 일정의 구성과 대조합니다.
```plain text
1) 상품의 타깃 · 콘셉트 키워드로 기대 콘텐츠 프로파일을 조회한다
   예) 타깃=20대 / 콘셉트=감성  →  기대 = {체험, 야간콘텐츠, 로컬F&B}

2) 실제 일정의 구성을 집계한다
   - contentTypeId 분포 (공사 API)
   - 시간대 분포 (19:00 이후 일정 존재 여부 = 야간콘텐츠)
   - 신분류체계 소분류 (공사 API)

3) 기대 프로파일 항목 중 일정에 0건인 것을 찾는다

판정 : 주의 — 20대 타깃 상품이지만 야간 콘텐츠와 체험형 콘텐츠가
       일정에 포함되어 있지 않습니다
제안 : 2일차 저녁 자유시간(20:00~) 구간에 반영 가능
```
기대 프로파일 테이블은 설정 화면에서 편집할 수 있으며, 초기값은 공사 관광 유형 분류를 기준으로 제공합니다.
<callout icon="🎯" color="gray_bg">
	**R10은 "이 상품이 잘 팔린다/안 팔린다"를 말하지 않습니다.**
	"타깃으로 선언한 고객층이 기대할 만한 콘텐츠 유형이 일정에 실제로 들어 있는가"라는 **구성 정합성**만 판정합니다. 원칙 4의 구현입니다.
</callout>

## 7-8. 규칙 확장 구조
규칙은 인터페이스 하나로 정의되며, 새 규칙 추가 시 기존 코드를 수정하지 않습니다.
```java
public interface AuditRule {
    String   code();             // R01
    String   version();          // 1.0.0
    Severity defaultSeverity();
    boolean  requiresExternal(); // 외부 데이터 필요 여부 → 출처 배지 결정
    List<Finding> evaluate(ItineraryContext ctx);
}
```
`requiresExternal()`이 true인 규칙의 판정 결과에는 화면에서 자동으로 "외부 참고" 배지가 붙습니다. 공사 데이터 기반 판정과 섞이지 않도록 구조적으로 보장하는 장치입니다.

## 8-2. 처리 파이프라인
```plain text
공사 API 원문
     ↓
[0] 구분자 분해 — ‘/’ ‘,’ ‘·’ 로 쪼개 여러 규칙을 분리  ← 실측 반영
     ↓ 조각단위로
[1] 규칙 기반 사전 파서 — 빈출 패턴을 정규식으로 처리 (LLM 호출 없음)
     ↓ 실패한 조각만
[2] LLM 정규화 — 스키마 고정 JSON 출력, temperature 0
     ↓
[3] 조각 병합 — 분해했던 결과를 하나의 운영규칙으로 합침
     ↓
[4] 스키마 검증 — 형식 불일치 시 확인 불가로 강등
     ↓
[5] 규칙엔진 판정 — 결정론적. AI는 여기 관여하지 않음
     ↓
[6] 화면 표시 — 판정 결과 + 정규화 결과 + 공사 원문 3단 병기
```
<callout icon="🎯" color="blue_bg">
	**커버리지 목표** — **90% 이상** · 커버리지 = 해석 성공 ÷ (전체 − 결측)
	분모에서 결측을 제외합니다. 결측은 해석 실패가 아니라 정상 산출물이며, 분모에 포함하면 휴무일은 최대 83.3%(239/287)라 90% 달성이 수학적으로 불가능해집니다. 이 기준의 착수 시점 실측은 **휴무일 85.8%(205/239) · 운영시간 76.7%(204/266)**이고, 통과선은 **216건 / 240건**입니다.
	실측에서 미분류로 빠졌던 것 중 `상시 개방` 계열(54건)과 `명절` 계열(19건) 두 패턴만 추가해도 운영시간은 76.7% → **97.0%**, 휴무일은 85.8% → **93.7%**로 오릅니다. 여기에 구분자 분해를 더하면 복합 표현이 대량 커버됩니다.
	나머지는 LLM에 위임하고, 그리고도 실패하면 확인 불가로 내립니다. 테스트 데이터는 실측한 287건을 그대로 사용합니다.
</callout>
<callout icon="💡" color="green_bg">
	**1단계를 규칙 기반으로 두는 이유**
	빈출 패턴 대부분은 정규식으로 처리됩니다. LLM 호출이 줄어 비용과 지연이 감소하고 재현성도 높아집니다. LLM은 잔여 케이스만 담당합니다.
</callout>
## 8-3. 확인 불가 항목의 활용
파싱 실패는 실패가 아니라 **산출물**입니다. 검수 리포트 말미에 다음 섹션이 자동 생성됩니다.
> **출시 전 직접 확인 필요 목록 (3건)**<br>1. A미술관 — 운영시간 정보 없음 · 문의처 033-000-0000<br>2. B전망대 — usetime 원문 "홈페이지 참조" · 홈페이지 링크<br>3. C체험관 — 휴무일 정보 없음
실무자가 전화 돌릴 대상을 정확히 알려주는 것. 데이터 공백을 은폐하지 않는 설계가 오히려 실용성을 만듭니다.

## 9-2. 패치 제안
검수에서 발견된 문제마다 수정안을 생성합니다. 수정안은 추상적 제안이 아니라 **그대로 반영 가능한 구체적 일정 변경**입니다.
사용자가 고른 수정안들을 모아, **전부 반영했을 때의 일정표를 전후로 대조**해 보여줍니다.
```plain text
선택한 수정안 4건을 모두 반영했을 때

현재                          반영 후
10:00 오죽헌 — 휴관일    →   10:00 선교장 — 연중무휴 · 4.2km
14:00 안목해변               14:00 안목해변
18:00 저녁식사               18:00 저녁식사
20:00 자유시간              19:30 강릉 야간 해변축제
                              21:30 숙소 체크인

수정안 간 충돌 검사  ✓ 충돌 없음

         [ 확정하고 재검수 ]   [ 선택 다시하기 ]
```
선택된 수정안들이 같은 일정 항목을 동시에 건드리거나 반영 후 같은 시간대에 몰리는 경우, **확정 전에 충돌을 표시**해 하나를 해제하도록 안내합니다.
## 9-3. 확정 즉시 재검수
확정하면 선택된 수정안을 **일괄 반영**한 뒤 전체 규칙을 **1회** 다시 실행합니다. 수정이 새로운 오류를 만들지 않았는지 확인하는 것이 핵심입니다.
- 대체 관광지가 해당 날짜에 실제로 운영하는가 (R01)
- 행사가 여행일에 개최되는가 (R02)
- 변경된 일정이 다른 일정과 겹치지 않는가 (R03)
- 대체 관광지 투입으로 콘텐츠 유형이 편중되지 않았는가 (R04)
- 대체 관광지의 운영정보를 데이터에서 확인할 수 있는가 (R05)
- 재조회 시점에 공사 데이터가 바뀌지 않았는가 (R06)
- 장시간 일정이 되어 식사·휴식이 누락되지 않았는가 (R07)
- 변경된 동선의 이동시간이 충분한가 (R08)
- 야외 비중이 높아져 우천 리스크가 커지지 않았는가 (R09)
- 타깃이 기대하는 콘텐츠 구성이 유지 또는 개선되었는가 (R10)
- 숙소 체크인 가능 시간을 넘기지 않는가

## 9-5. 영향받는 상품 자동 탐색
변경이나 신규 행사가 감지되면 등록된 기존 상품 중 영향을 받는 것을 자동으로 찾습니다.
**탐색 조건**
1. 해당 contentid를 일정에 포함한 상품 (직접 영향)
2. 동일 지역(법정동 코드)을 방문하는 상품
3. 행사기간과 여행일이 겹치는 상품
4. 관광 콘텐츠 유형(contentTypeId)이 유사한 상품
5. 일정에 추가 가능한 빈 시간대가 있는 상품
6. 추가 시 이동거리 증가가 임계치 이하인 상품
1\~3은 **위험 알림**(지금 상품이 깨졌다), 4\~6은 **기회 알림**(지금 상품을 개선할 수 있다)으로 구분해 표시합니다.
> **상품 변경 알림** · 위험<br>9월 15일 출발 예정인 '부산 야경투어'의 A전망대 운영시간이 변경됐습니다.<br>기존 일정대로 방문하면 입장 가능시간이 20분밖에 남지 않습니다.<br>A전망대와 B야시장의 방문 순서를 교체하면 정상 운영할 수 있습니다.
## 9-6. 수요 기회 발견
상품이 깨지지 않았더라도 더 좋아질 수 있는 여지를 찾아 제안합니다. R10의 결손 진단과 T1·T2 수요 신호를 결합한 결과입니다.
```plain text
기존 상품  : 강릉 2030 감성여행 / 타깃 20대 / 콘셉트 감성
R10 진단  : 주의 — 기대 콘텐츠 중 야간·체험형이 일정에 0건
T2 신호   : 여행기간 중 강릉 지역 행사 3건 개최 (공사 행사정보)
            그중 1건이 야간 해변축제 → R10 결손 유형과 일치
제안      : 2일차 저녁 자유시간을 야간 해변축제로 대체 가능
            추가 이동시간 18분 · 다른 일정과 충돌 없음 (R03·R08 사전 검증 통과)
```
<callout icon="📊" color="yellow_bg">
	**TourLint는 상품 판매량을 예측한다고 주장하지 않습니다.**
	제공하는 것은 다섯 가지뿐입니다 — 공사 데이터에서 관측된 수요 신호, 기존 상품과의 연관성, 반영할 수 있는 일정 구간, 수정에 따른 운영 가능성, 수정 후 재검수 결과.
	시장 반응을 예측하는 것은 기획자의 판단 영역입니다.
</callout>

## 12-3. 데이터 취득 원칙
- 관광지·행사 정보는 **전량 공사 OpenAPI 실시간 호출**로 취득합니다. 파일 형태 데이터를 내려받아 사용하지 않습니다
- 엑셀 업로드 기능의 대상은 **이용자가 작성한 상품 일정표**이며, 공사 관광데이터가 아닙니다
- 이미지는 공사가 제공하는 URL을 직접 참조하며 서버에 저장하지 않습니다
- 공사가 제공한 원문 데이터는 수정하지 않습니다. 자체 산출물과는 출처 배지로 구분합니다
- 응답은 `_type=json`으로 수신하며, 20km 반경 제한이 있는 오퍼레이션은 그 범위 내에서만 사용합니다
- **커스텀 오퍼레이션은 요청하지 않습니다.** 제공되는 오퍼레이션 조합만으로 전 기능을 구현합니다

### 3단 대응
**① 온디맨드 우선** — "지금 재검수" 버튼이 1급 기능이고 자동 배치는 부가 기능입니다. 사용자가 필요할 때 호출하는 구조가 공공 API 사용에 적합하며, 시연에서도 즉시 결과가 나오는 쪽이 효과적입니다.
**② 2단계 경량 배치**
<callout icon="🔑" color="blue_bg">
	배치는 상세정보를 전부 다시 가져오지 않습니다.
	**1단계** 공사가 권고한 동기화 목록 조회로 `modifiedtime`에 하루치 날짜를 넣어 그날의 변경분을 받습니다. 공사는 당일 수정분이 익일 반영되므로 **전일 날짜로 호출**하라고 안내했습니다
	**1단계-b** 같은 응답의 `showflag`로 표출 중단 콘텐츠를 함께 판독합니다. 실측 결과 미지정 호출에 표출·비표출이 모두 포함되므로 **별도 조회가 필요 없습니다**
	**2단계** 수정일자가 바뀐 콘텐츠 중 우리 상품에 포함된 것만 상세정보 재호출
	조회 기준일은 전일 고정이 아니라 **직전 배치 성공일의 다음 날**부터 어제까지를 **하루씩 순회 호출**합니다. `modifiedtime`은 실측 결과 해당일 분만 반환하므로(누적 아님) 구간을 한 번에 받을 수 없습니다.
	공사는 회신에서 서비스를 두 그룹으로 나누어, **국문은 04:30 이후면 최신 수정일자 기준으로 업데이트된 데이터를 반영할 수 있다**고 명시했습니다. 07:00 회차는 고캠핑·두루누비·오디오·관광채용·빅데이터 등 **다른 그룹의 동기화 시각**이며, TourLint가 활용하는 서비스는 그 그룹에 하나도 없습니다. 따라서 **05:00 배치 한 번으로 전일 수정분을 빠짐없이 받습니다.**
	배치를 건너뛰거나 실패한 구간은 `last_covered`(마지막으로 조회 완료한 기준일)를 **성공했을 때만 갱신**하는 것으로 커버됩니다. 주말 스킵 후 월요일 배치가 금·토·일을 함께 훑는 것도 같은 원리입니다.
	다만 **평일 조회 결과가 0건이면 ****`last_covered`****를 갱신하지 않습니다.** 평일 변경 건수는 실측상 수십 건이므로 0건은 공사 동기화 지연 신호로 보고, 다음 배치가 그 날짜를 다시 조회합니다
</callout>

```plain text
[실측] 2026-08-12 오퍼레이션 동작 확인 (개발계정 직접 호출)
       modifiedtime  해당일 분만 반환 (누적 아님) → 구간은 날짜별 순회 호출
       showflag      미지정 시 표출·비표출 모두 반환 → 별도 조회 불필요
       numOfRows     2000까지 동작 확인 (100 아님) → 1000 사용

[기존] 50건 × 29콜                            = 1,450콜
[개선] 평일 05:00 1회
         1단계  변경분 + 비표출 (하루치)     1콜
         2단계  겹치는 것만 상세 재호출      약 3콜
                                          ─────
                                          약 4콜 / 평일
       월요일  금·토·일 3일 순회            약 6콜
       주말                                 0콜

       → 약 1/360 수준 · 주말 제외로 더 감소
```
<callout icon="⚠️" color="yellow_bg">
	**위 수치는 가정이 아니라 30일간 실측값입니다.** 2026-08-05에 개발계정으로 `areaBasedSyncList2`를 60회 호출해 일별 `totalCount`를 수집했으며, 원본은 `daily_changes.csv`로 보관합니다.
	다만 **비표출은 대량 발생할 수 있습니다.** 2026-07-28에는 하루에 3,206건이 전환되었고, 2026-08-12 재확인 결과 그날 전체 3,324건 중 비표출이 3,206건이었으며, 다음날(7/29)에도 295건의 여진이 있었습니다. 중요한 것은 이것이 `modifiedtime` 조회에 그대로 잡힌다는 점입니다. 배치에 **비표출 조회 페이지 상한(기본 20)**을 안전장치로 두되, 실질적으로 걸릴 일은 없습니다. `numOfRows`가 **2000까지 동작**하는 것이 실측으로 확인되어, 1000 기준 **4콜**이면 3,206건을 전량 수신합니다.
</callout>
**③ 예산 관리자 내장**
```plain text
- 일일 호출 예산을 설정하고 실시간 카운트
- 예산 80% 도달 시 배치 자동 중지
- 오퍼레이션별 호출 이력을 대시보드에 표시
- 개발 기간 중 배치 기본 OFF, 데모 상품 10건 상한
```
호출 로그는 자체 보관하여 1차 심사 제출 시 API 활용 근거로 함께 제시합니다.
<callout icon="✅" color="green_bg">
	**호출 예산 관리자를 감춰진 방어 장치가 아니라 제품 기능으로 노출합니다.**
	공공 API를 절제해서 쓰는 설계 자체가 서비스의 성숙도를 보여주는 지표입니다.
</callout>
**④ 사전 협의 경로 확보**
공사는 로컬 서버 저장 승인 회신에서 "서버에 데이터를 저장하기 위해 일시적인 트래픽 증설이 필요할 경우" 연락하도록 안내했습니다. 안내 범위가 저장을 위한 호출로 한정되어 있으므로, 시연 데이터 구축을 위한 초기 일괄 검수(W7)만 이 경로에 해당합니다.
비표출 대량 전환이나 운영계정 승인 지연은 저장을 위한 호출 증가가 아니므로 이 경로에 포함하지 않고, 페이지 상한과 예산 관리자로 자체 해결합니다.

- [ ] 실제 배포된 웹 서비스 + 테스트 계정
## 14-2. 우선순위 조정 원칙
<callout icon="🎚️" color="yellow_bg">
	일정이 밀릴 경우 **기능을 삭제하지 않고 아래 순서로 범위를 축소**합니다. 가장 먼저 자르는 것은 **자연어 붙여넣기**이며, 엑셀 지정 양식과 직접 입력만 남깁니다. LLM 의존도와 F01 개발량이 가장 크게 줄어드는 지점입니다. 화면에서 기능이 사라지는 것보다 범위가 좁아지는 편이 완성도에 유리합니다.
	1. **R09 1단계 축소** — 예보 연동을 생략하고 기상청 과거관측 기반 **평년 통계만** 사용
	2. **R09 2단계 축소** — 평년 통계 취득도 어려우면 **지역·월별 강수일수 고정 테이블**로 대체 (외부 API 의존 완전 제거)
	3. **R10 축소** — 기대 콘텐츠 프로파일을 설정 화면 편집 불가·고정 테이블로 제공
	4. **T1 축소** — 신규 콘텐츠 감지 주기를 일 단위에서 수동 트리거로 전환
	5. **엑셀 업로드 축소** — 지정 양식 1종만 지원 (컬럼 매핑 UI 생략)
	6. **PDF 리포트 축소** — 화면 인쇄용 레이아웃으로 대체
</callout>
## 14-3. 범위 제외
<callout icon="🚧" color="gray_bg">
	범위를 명시적으로 닫는 것이 완성도를 만듭니다. 아래는 이번 개발 범위에서 **의도적으로 제외**합니다.
	- 한글·워드·PDF 자유 양식 완전 분석 (지정 엑셀 양식만 지원)
	- 실시간 공동 편집
	- 조직별 승인 워크플로
	- 예약·결제·판매채널 연동
	- 판매량 예측
	- 외부 SNS·뉴스·검색 트렌드 분석 (공사 데이터 기반 T1·T2로 대체)

	- 다국어 인바운드 상품 검수
	- 여행사 ERP 연동
	- 이메일·푸시 알림 (화면 내 알림만)
	- 이용자 위치 기반 기능 (설계 원칙상 영구 제외)
</callout>

	검증할 수 없는 것은 검증할 수 없다고 표시합니다.

## 15-2. 배포 전략
1차 심사 제출 항목에는 **활용 API 신청정보(신청자명, 인증키)** 가 포함되고, 운영계정은 **실서비스 URL을 제출한 뒤 승인**됩니다. 배포가 늦으면 승인이 마감을 넘길 수 있습니다.
<callout icon="🎯" color="orange_bg">
	**운영계정 신청을 위한 배포는 완성품일 필요가 없습니다.**
	규정이 요구하는 것은 "정상 서비스로 보이는" URL입니다. 따라서 배포를 개발 완료 시점까지 미루지 않고 **두 번에 나눕니다.**
	**① 8월 3주차 — 최소 배포.** 로그인 + 상품 등록 + 검수 결과 화면만으로 실서비스 URL을 먼저 확보합니다
	**② 8월 4주차 — 정식 배포.** 검수 엔진 전체가 동작하는 상태로 8.28 서비스를 개시합니다. 승인 요건이 상용 런칭 확인이므로 운영계정 신청은 런칭 이후에 넣습니다
	**③ 8월 4주차 — 활용 증빙 패키지 준비.** 공사는 내부 데이터로 활용하는 경우 화면·기능 캡처를 메일로 제출하도록 안내했습니다. 신청과 동시에 내면 승인이 빨라집니다
	이후 기능은 배포된 서비스 위에 계속 얹습니다. 배포가 마일스톤이 아니라 **개발 초기에 끝내는 인프라 작업**이 됩니다.
	**활용 증빙으로 제출할 화면** — TourLint는 관광지 정보를 나열하는 서비스가 아니라 판정 근거로 소비하는 구조이므로, 어느 화면이 증거인지를 미리 정리해 둡니다.
	① 동명 장소 확정 화면 — 검색 결과에 contentid·주소·유형 표시 (관광지 매칭이 공사 데이터로 이루어짐)
	② 검수 결과 화면 — 공사 원문 / AI 해석 / 판정 3단 병기 (판정이 공사 원문에 근거함)
	③ 검수 근거 영역의 조회 시각·데이터 지문과 호출 예산 위젯 (실시간 호출이 실제로 발생함)
	④ R02 판정 화면 — eventstartdate/enddate 원문 병기 (행사 데이터 활용)
	⑤ 자체 보관 중인 오퍼레이션별 호출 로그 · 전 화면 하단 출처 표기
</callout>

# 19. 범위 확정 · 확장 로드맵 (2026.08.19 팀 합의)
## 19-1. 확정 범위
검수 대상은 **국내 당일 · 1박 2일 · 2박 3일(박수 0 · 1 · 2), 상품당 최대 구간 12곳**이다. 성능 목표는 8곳 이하 p95 15초 · 12곳 p95 20초, 검수 1회 호출량은 8곳 약 29콜 · 12곳 약 43콜로 산정한다(12-4). **3박 이상은 등록 자체를 지원하지 않는다.**
## 19-2. 왜 2박 3일까지인가
온디맨드(동기) 검수가 "기다릴 만한" 한계가 12곳 · 20초 수준이다. 3박 4일부터는 콜수와 시간이 비례 증가해 30초를 넘어서므로, 접수 → 진행률 → 완료 알림의 **비동기 검수 구조 전환**이 선행되어야 한다. 범위를 숫자가 아니라 아키텍처 경계에서 자른 것이다.
## 19-3. 2차 확장(3박 4일 이상) — 수상 이후 검토
공공데이터포털 운영계정 전환(일 100,000콜)과 비동기 검수 도입을 전제로 한 2차 확장으로 남긴다. 상세 절차는 [확장 로드맵 문서](https://app.notion.com/p/3c1ec0325d5b81bbb6b2e2a37a4fc4a2)를 기준으로 하며, 심사기간(10.01–11.05)에는 어떤 확장도 배포하지 않는다(NF-AV-010).
