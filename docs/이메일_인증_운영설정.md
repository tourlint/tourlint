# 신규 가입 이메일 인증 운영 설정

2026.09.18 · #539 · Resend

기존 계정과 심사용 계정은 이메일·비밀번호로 계속 로그인한다. 신규 가입만 이메일로 받은 6자리 코드를 확인한 뒤 계정·기본 설정·세션을 생성한다. 기존 계정을 이메일 인증 완료 계정으로 소급 표시하지 않는다.

## Resend 준비

1. https://resend.com 에 가입한다.
2. Domains에서 **실제로 소유한 발신 도메인**을 등록한다. 예: `tourlint.kr` 또는 메일 발송 전용 서브도메인. 서비스가 Railway 주소로 열리는 것과 발신 도메인 소유·인증은 별개다.
3. Resend에 표시되는 DNS 레코드를 도메인 관리 서비스에 추가한다. 기존 수신 메일의 MX 레코드를 임의로 덮어쓰지 않는다. 표시된 호스트명과 값을 그대로 사용한다.
4. 상태가 `Verified`인지 확인한다.
5. API Keys에서 해당 발신 도메인으로 범위를 제한한 **Sending access** 키를 만든다.
6. Railway → TourLint → production → **api** → Variables에 아래 두 값을 넣는다. web 서비스·NEXT_PUBLIC 변수·GitHub·채팅에는 키를 넣지 않는다.

| 이름 | 값 |
|---|---|
| `RESEND_API_KEY` | 생성한 발송 API 키 |
| `AUTH_EMAIL_FROM` | 인증된 도메인의 발신 주소. 예: `TourLint <noreply@tourlint.kr>` |

`onboarding@resend.dev`는 Resend 계정 소유자에게만 보낼 수 있는 테스트 발신 주소이므로 일반 회원가입용으로 쓰지 않는다. 키가 없거나 발송에 실패하면 503 안내를 반환하며 인증을 우회하지 않는다.

공식 문서: [도메인 인증](https://resend.com/docs/dashboard/domains/introduction), [API 키](https://resend.com/docs/dashboard/api-keys/introduction), [이메일 발송 API](https://resend.com/docs/api-reference/emails/send-email).

## 배포 순서

1. 위 발신 설정을 완료한다.
2. 운영 DB에 `db/migrations/2026-09-18_signup_verification.sql`을 적용한다. 기존 데이터는 변경하지 않고 두 테이블만 추가한다.
3. CI가 통과한 기능 PR을 dev에 머지하고, 별도 release PR로 main에 반영한다.
4. 배포 완료 후 `/health`의 커밋과 `checks.signupEmail: ok`, `checks.schema: ok`를 확인한다. `signupEmail`은 설정 존재 여부만 검사한다. 실제 발신 권한·도달 여부를 보증하지 않는다.
5. 운영 가입 화면에서 소유한 수신 이메일로 코드를 요청해 실제 메일을 확인하고 가입·로그인·로그아웃을 점검한다. 메일 수신 검증 전에는 운영 완료로 판정하지 않는다.
6. 기존 심사용 계정의 로그인과 준비된 상품이 그대로인지 확인한다.

## 동작과 제한

- 코드 유효기간 10분, 코드당 오입력 5회. 재전송 시 이전 코드는 무효다.
- 재전송 간격 60초, 이메일당 시간당 5회. 서비스 전체 분당 10회·UTC 날짜당 100회. 한도는 DB에 저장돼 재배포로 초기화되지 않는다. 발송 실패도 요청 한도에 포함한다.
- 코드 원문은 메일 외에는 DB·응답·로그에 남기지 않는다. 임시 인증 저장소에는 scrypt 해시를 둔다.
- 이메일에 연결된 UUID와 코드가 모두 맞아야 가입 가능하다. 계정 생성과 코드 소비는 하나의 트랜잭션이며 동시에 여러 요청이 와도 한 번만 소비한다.
- 메일 공급자와 통신하는 동안 DB 잠금을 잡지 않는다. 발송 실패 시 해당 코드만 무효화한다.
- 마지막 발송이 24시간 지난 인증 행과 만료된 전역 한도 버킷을 매시간 정리한다. IP 등 추가 개인정보는 저장하지 않는다.
- 인증메일은 기존 계정 주소에도 같은 형태로 보내 계정 존재 여부를 요청 응답으로 구별하지 않는다. 코드가 맞아도 이미 있는 계정의 비밀번호를 변경하거나 새 로그인 세션을 발급하지 않는다.
- 별도의 비밀번호 재설정·소셜 로그인 기능은 이번 변경에 포함하지 않는다.

## 검증 기록

HTTP 및 실제 PostgreSQL 테스트에서 정상 가입, 무인증 가입 차단, 다른 이메일, 만료, 오입력 5회, 미발송, 재사용, 재전송, 동시 소비, 계정 생성 실패 롤백, 이메일·전역 한도, 메일 오류, 기존 일반·심사용 계정 로그인을 확인한다. 10개 보안 가드를 각각 제거했을 때 해당 테스트가 실패하는 것도 확인했다.

로컬 브라우저에서는 메일 발송만 테스트용 어댑터로 대체해 코드 입력·오류 안내·가입 후 홈 이동을 확인했다. 이 검증은 실제 이메일 수신 확인과 구분한다.
